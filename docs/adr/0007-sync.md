# ADR-0007: Синхронизация зашифрованных объектов

- Статус: принято
- Дата: 2026-09-28
- Основание: [ADR-0005](0005-local-first-e2ee-architecture.md), Stage 3 и §8 (в документе владельца — «ADR-003»)
- Код: контракт — `packages/shared/src/schemas/sync.ts`, квоты — `packages/shared/src/entitlements.ts`;
  сервер — `apps/api/src/modules/sync/*`, `apps/api/src/modules/entitlements/usage.ts`, таблица `objects` в
  `apps/api/src/db/schema.ts`; клиент — `apps/web/src/vault/{db,objects,impactRepository}.ts`, транспорт
  `apps/web/src/api/sync.ts`, движок `apps/web/src/sync/{engine,runtime,idbStore,content}.ts`, Vue-обёртка
  `apps/web/src/composables/useSync.ts`; проверка против настоящего API — `apps/web/scripts/sync-e2e.ts`
- Справочник API: [docs/api.md](../api.md), раздел «Синхронизация»

## Контекст

Запись создаётся и живёт на устройстве; сервер — реплика шифротекстов, а не источник истины в открытом
виде. Нужно: работа офлайн, несколько устройств, никаких потерь при одновременной правке и при этом
никакого знания о содержимом на сервере. Журнал в основном пополняется, одновременная правка одной записи
редка — CRDT не нужен (ADR-0005).

## Решение

### 1. Модель объекта

Сервер (`objects`, первичный ключ `(user_id, object_id)`, индекс `(user_id, seq)`) — **одна строка на
объект**, последнее состояние:

| Поле | Смысл |
| --- | --- |
| `object_id` | UUID v4, генерирует клиент (`newId()`); стабилен всегда, не зависит от сервера и региона |
| `kind` | вид объекта; сейчас только `impact` (`OBJECT_KINDS`) |
| `version` | целое ≥ 1, растёт на 1 при каждой принятой записи (включая удаление) |
| `ciphertext` | зашифрованный объект v1 (ADR-0006) или `null` для tombstone |
| `deleted` | tombstone |
| `seq` | `nextval('object_seq')` при каждой записи — монотонный курсор для pull |
| `updated_at` | время записи на сервере |

Клиент (IndexedDB `impact-log`, `apps/web/src/vault/db.ts`):

- `objects` — `{ objectId, kind, ciphertext | null, version, dirty: 0|1, deleted: 0|1, updatedAt }`;
  `version` — последняя известная серверная версия (0 — объект ещё не синхронизирован), `dirty = 1` —
  есть неотправленные изменения (индекс `dirty`);
- `conflicts` — `{ objectId, kind, server: { version, ciphertext, deleted }, detectedAt }`;
- `meta.sync` — `{ cursor, lastSyncAt }`.

Шифротекст в IndexedDB и на сервере один и тот же: синхронизация ничего не перешифровывает.

### 2. Локальная запись первой

`EncryptedImpactRepository` (реализация `ImpactRepository` из core):

- `save` — шифрует запись, кладёт объект с `dirty = 1`, сохраняя известную `version`;
- `remove` — если сервер об объекте не знает (`version = 0`), удаляет локально; иначе оставляет tombstone
  (`ciphertext = null`, `deleted = 1`, `dirty = 1`), чтобы удаление дошло до других устройств.

UI получает подтверждение сразу после локальной записи; сеть — асинхронно.

### 3. Доступ к `/api/sync/*`

Проверки выполняются в хуке `onRequest` — до разбора тела, так что push в 8 МиБ с чужим аккаунтом или
сверх лимита даже не парсится:

1. **Полная сессия** (привязана к устройству, ADR-0008), иначе `401`.
2. **Лимит частоты на пользователя**, а не на IP: `SYNC_RATE_LIMIT_MAX` запросов в минуту (по умолчанию
   120) → `429 RATE_LIMITED`. Рост хранилища ограничивается по аккаунту, смена IP не помогает.
3. **Заголовок `X-Impact-Account`** (`SYNC_ACCOUNT_HEADER`) с публичным `accountId` аккаунта, к которому
   привязано локальное хранилище. Нет заголовка (или пустой) → `400 VALIDATION_ERROR`; не совпадает с
   пользователем сессии → `409 ACCOUNT_MISMATCH`.

Зачем заголовок: cookie сессии общая для всех вкладок браузера. Если в соседней вкладке вошли в другой
аккаунт, без сверки движок этой вкладки отправил бы объекты хранилища аккаунта A в аккаунт B (под чужим MK)
или скачал бы объекты B. Web-клиент без привязанного аккаунта запрос не отправляет вовсе
(`apps/web/src/api/sync.ts`).

### 4. Push

`POST /api/sync/push` (полная сессия), тело `{ changes: [{ objectId, kind, baseVersion, ciphertext | null }] }`.
`baseVersion` — версия, от которой сделано изменение (0 — новый объект), `ciphertext: null` — удаление.

Сервер применяет изменения по порядку в одной транзакции. Пуши одного пользователя сериализуются
блокировкой его строки (`SELECT … FROM users … FOR UPDATE`), поэтому `seq` внутри пользователя выдаются в
порядке коммитов и pull по курсору не может «перепрыгнуть» ещё не закоммиченное изменение. Результат —
по одному на изменение:

| Условие (проверяется по порядку) | Результат |
| --- | --- |
| объекта нет, а `baseVersion > 0` | `rejected`, `INVALID` |
| объекта нет, а `ciphertext = null` (удаление несуществующего) | `rejected`, `INVALID` |
| объект есть, но другого `kind` | `rejected`, `INVALID` |
| объект есть и `version ≠ baseVersion` | `conflict` + `server` (текущая серверная ветка); ничего не перезаписано |
| создание impact (объекта нет или он tombstone, `ciphertext ≠ null`) сверх `maxActiveImpacts` | `rejected`, `QUOTA_EXCEEDED` |
| рост хранилища (новый живой объект или больше байт шифротекста) сверх `maxObjects` / `maxStorageBytes` | `rejected`, `QUOTA_EXCEEDED` |
| иначе | `accepted`, `{ version: прежняя + 1, seq }` |

Удалить можно только существующий объект: tombstone «из ничего» отклоняется — иначе клиент мог бы раздувать
хранилище строками без содержимого.

### 5. Pull

`GET /api/sync/pull?cursor=<seq>&limit=<n>` (полная сессия, `X-Impact-Account`) → `{ changes, cursor, hasMore }`:

- изменения пользователя с `seq > cursor` по возрастанию `seq`, не больше `limit` (по умолчанию 500,
  максимум 1000) и не больше `PULL_MAX_BYTES` = 8 МиБ суммарного шифротекста — но в странице всегда есть
  хотя бы один объект (он сам не больше 256 КиБ);
- сервер сначала читает только `seq` и размеры (`octet_length`, без распаковки TOAST), `limit + 1` строк —
  чтобы честно определить `hasMore`, — затем сами объекты до последнего взятого `seq`. Объект, обновлённый
  между этими запросами, получает новый `seq` и придёт на следующей странице;
- объект приходит **в последнем состоянии**, одной записью; промежуточные версии не хранятся и не отдаются;
- `cursor` в ответе — `seq` последнего отданного изменения (или прежний, если изменений нет), `hasMore` —
  есть ли ещё; клиент повторяет pull, пока `hasMore`.

Свои же принятые изменения тоже вернутся в pull — клиент узнаёт их по совпадению `version`.

### 6. Клиентский движок

Движок (`apps/web/src/sync/engine.ts`) — чистый алгоритм без Vue, IndexedDB и `fetch`: хранилище
(`SyncStore`, реализация `idbStore.ts`) и транспорт (`SyncTransport`, `src/api/sync`) — адаптеры. Все
решения по объекту принимаются внутри одной транзакции IndexedDB по актуальному состоянию
(compare-and-set): пользователь мог изменить запись, пока шёл сетевой запрос.

**Цикл:** pull до `hasMore = false` (курсор сохраняется после каждой страницы) → push всех `dirty` →
повторный pull, если были конфликты. Одновременно идёт один цикл, вызовы во время цикла схлопываются в
один следующий.

Правила:

1. **Курсор двигает только pull.** `seq` из результата push курсор не сдвигает: изменение другого
   устройства могло закоммититься раньше с меньшим `seq`.
2. **Pull не затирает несинхронизированное.** Чистый (`dirty = 0`) объект заменяется серверным; если
   локальный объект `dirty` и серверная версия новее, это конфликт, а не обновление. Если содержимое обеих
   веток совпадает (сравнение расшифрованных записей без учёта `updatedAt`), конфликт не заводится.
3. **Конфликт без потерь.** Серверная ветка сохраняется в `conflicts` (если сервер ушёл дальше —
   обновляется до самой свежей), локальная остаётся в `objects` (`dirty = 1`) и не отправляется, пока
   конфликт не разрешён. Разрешает пользователь (`resolve`):
   - `local` — локальная ветка отправляется с `baseVersion = server.version` (в том числе локальное
     удаление — тогда запись удаляется и на сервере);
   - `server` — локальная заменяется серверной (или удаляется, если на сервере tombstone);
   - `both` — серверная ветка остаётся под своим `objectId`, локальная сохраняется **новой записью**
     с новым `objectId` и пометкой в заголовке; её приходится перешифровать, потому что AAD привязан к
     `objectId` (ADR-0006).
4. **Порядок push:** удаления → правки → создания, чтобы удаления освобождали квоту в том же push.
   Пачки — до 100 изменений и 4 МиБ (запас к серверным 200 / 8 МиБ); на `413` пачка уменьшается вдвое,
   объект, который не влезает даже один, помечается `TOO_LARGE`. Объект с шифротекстом больше 256 КиБ не
   отправляется вовсе (`TOO_LARGE`).
5. **Отказ по квоте** (`QUOTA_EXCEEDED`) не трогает локальную запись: она остаётся `dirty`, считается в
   `quotaBlocked` и не отправляется повторно, пока место не освободится (удаление — своё или пришедшее
   через pull) или не сменится тариф.
6. **`INVALID`:** для tombstone'а — локальный tombstone просто забывается (сервер «не знает» объект —
   удалять нечего; tombstone несуществующего объекта сервер отклоняет);
   для объекта, который сервер «не знает» (`version > 0`), — объект отправляется заново как новый; для
   нового объекта — помечается `INVALID` и больше не отправляется. Локальные данные не удаляются.
7. **Свои изменения** распознаются по версии и шифротексту принятых push (гонка «экран прочитал старую
   версию, а движок уже записал принятую» — не конфликт).
8. **Запись только под своим MK.** Каждая транзакция записи (движка и репозитория) сверяет отпечаток MK
   вкладки с `meta.vault.mkId` (`assertVaultKey`, ADR-0006). Если другая вкладка успела сменить MK (вход в
   аккаунт), запись отклоняется (`VAULT_CHANGED`), и вкладка перезагружается — старым ключом ничего не
   пишется.

Среда выполнения (`apps/web/src/sync/runtime.ts`):

- триггеры — вход в аккаунт, локальные изменения (debounce 1,5 с), фокус, видимость вкладки, `online`,
  раз в минуту при видимой вкладке; `offline` → статус `offline`;
- ошибки сети, 5xx и `429` — экспоненциальный повтор от 2 с до 5 минут (±20 %); `401` → `signed-out`,
  цикл останавливается, данные остаются локально;
- `409 ACCOUNT_MISMATCH` → синхронизация **останавливается без повторов** (статус `error`,
  `lastError = ACCOUNT_MISMATCH`), локальные данные не трогаются; пользователь входит в нужный аккаунт, и
  «Синхронизировать сейчас» проверяет заново. Перед любым входом web-клиент сам останавливает синхронизацию
  (`sync.stop()`), потому что вход меняет cookie сессии;
- синхронизирует одна вкладка — владелец Web Lock `impact-log-sync`; остальные получают её состояние и
  просят синхронизацию через `BroadcastChannel` `impact-log-sync` (без Web Locks — каждая вкладка сама);
- раз в 10 минут обновляет профиль тарифа и использование (`GET /api/entitlements`).

Состояние для UI — `useSync()`: `status` (`off | idle | syncing | offline | signed-out | error`),
`pending`, `conflicts`, `quotaBlocked`, `lastSyncAt`, `lastError`, `retryAt`, `usage`.

### 7. Смена Master Key и отвязка аккаунта

Когда на устройстве есть записи другого хранилища, а пользователь регистрирует аккаунт (у нового аккаунта
всегда свой MK) или входит в существующий, хранилище переходит на MK аккаунта (`adoptMasterKey`, подробно —
ADR-0006 §8):

- при **регистрации** записи переносятся всегда (ради этого её и включают), переход — после подтверждения
  кода 2FA;
- при **входе и восстановлении** — только по явному выбору в диалоге (`components/MergeDialog`): «добавить в
  аккаунт» (по умолчанию), «стереть с устройства» или «отменить вход» (тогда только что открытая сессия
  закрывается, хранилище не тронуто). Если активных записей нет, диалог не показывается;
- смена ключа — одна транзакция IndexedDB под Web Lock `impact-log:rekey`, синхронизация на это время
  остановлена. DEK переоборачиваются, объекты, которые не удалось расшифровать, уходят в карантин
  (store `quarantine`, IndexedDB v2) и в синхронизацию не попадают;
- все перенесённые объекты становятся новыми для сервера (`version = 0`, `dirty = 1`), локальные
  tombstone'ы и конфликты удаляются, курсор сбрасывается в 0. Первый push таких объектов — это создание (к
  нему применяются квоты), первый pull с курсора 0 скачивает весь аккаунт.

### 8. Tombstone'ы

- Удаление — версионированный tombstone (`deleted = true`, `ciphertext = null`), он получает свой `seq` и
  доходит до всех устройств через pull. Tombstone бывает только у объекта, который был на сервере.
- Tombstone освобождает и байты шифротекста, и место в `maxObjects` (считаются только живые объекты); строка остаётся до компакции (TODO).
- «Воскрешение» (push с шифротекстом поверх tombstone'а с верным `baseVersion`) считается созданием и
  проходит проверку квоты.
- **Компакции нет:** tombstone'ы хранятся бессрочно. Для компакции нужно знать курсоры всех устройств —
  отложено (ADR-0005 это допускает).

### 9. Квоты

Сервер применяет в push три лимита профиля тарифа (ADR-0009); счётчики считаются один раз за push (лениво)
и дальше ведутся по ходу применения — под той же блокировкой строки пользователя, поэтому точны:

- `maxActiveImpacts` — **только создание** объектов `impact` (включая «воскрешение» tombstone'а). Обновления и
  удаления не ограничиваются, удаление сразу освобождает место — в том числе внутри того же push;
- `maxStorageBytes` — сумма байт шифротекстов всех объектов пользователя (`octet_length`);
- `maxObjects` — число **живых** объектов (tombstone'ы не считаются); все строки вместе с tombstone'ами — не больше `2 × maxObjects` (новая строка сверх потолка → `QUOTA_EXCEEDED`).

Лимиты хранилища ограничивают **только рост**: новую строку или увеличение шифротекста. Уменьшение и
удаление разрешены всегда, даже сверх лимита (например, после смены тарифа). Отказ — `rejected
QUOTA_EXCEEDED` для конкретного изменения. Клиентская проверка (`canCreateImpact` в `useImpacts`) — только
для UX; использование хранилища клиент видит в `GET /api/entitlements` (`usage.storageBytes`, `usage.objects`).

### 10. Лимиты

| Лимит | Значение | Где |
| --- | --- | --- |
| Шифротекст одного объекта | 256 КиБ | `MAX_OBJECT_CIPHERTEXT` |
| Изменений в одном push | 1–200 | `MAX_PUSH_CHANGES` |
| Тело push | 8 МиБ, иначе `413 PAYLOAD_TOO_LARGE` | `sync.routes.ts` |
| Pull, объектов | 500 по умолчанию, максимум 1000 | `PULL_LIMIT_DEFAULT`, `PULL_LIMIT_MAX` |
| Pull, байт | 8 МиБ шифротекста на страницу (минимум один объект) | `PULL_MAX_BYTES` |
| Частота | `SYNC_RATE_LIMIT_MAX` запросов в минуту на пользователя (по умолчанию 120) | `apps/api/src/config.ts` |
| Хранилище | `maxStorageBytes`, `maxObjects` из тарифа | ADR-0009 |

### 11. Что видит сервер

`objectId` (случайный UUID), вид, версия (сколько раз объект менялся), размер шифротекста, флаг удаления,
время и порядок изменений. Содержимое, даты события, заголовки, метки — нет.

## Последствия

- (+) Простой протокол: две ручки, одна таблица, никакого знания о содержимом.
- (+) Правки разных записей сливаются автоматически; одновременная правка одной записи не теряет данных.
- (+) Шифротекст переносим между регионами как есть (ADR-0011).
- (−) **Отличие от ADR-0005:** сервер хранит одну версию объекта, а не обе ветки конфликта. Проигравшая на
  сервере ветка живёт только на устройстве, где возник конфликт, — пока он не разрешён, потеря этого
  устройства означает потерю его ветки.
- (−) Нет истории версий на сервере — откатиться к старой версии записи нельзя (и сервер не может
  доказать, что не откатил объект сам, ADR-0006 §9).
- (−) Tombstone'ы копятся без компакции (строки в БД), хотя в `maxObjects` не входят; их число ограничено числом
  удалений. Компакция (например, после того как все устройства прошли курсор) — TODO.
- (−) Вложения в протокол не входят: большие блобы пойдут в отдельное хранилище (ADR-0005, Stage 6.5).

## Альтернативы

- **CRDT** (Automerge/Yjs) — отвергнуто ADR-0005: сложность не оправдана для журнала, где одновременная
  правка одной записи — редкость.
- **Last-write-wins на сервере** — теряет данные при конфликте и требует доверять часам клиента.
- **Хранить все ветки/историю на сервере** — ближе к тексту ADR-0005, но требует модели веток и их уборки;
  отложено, пока конфликты редки. Можно добавить, не меняя формат шифротекста.
- **Курсор по времени** (`updated_at`) — ненадёжен при одинаковых отметках и конкурентных транзакциях;
  монотонный `seq` под блокировкой пользователя проще и точнее.
